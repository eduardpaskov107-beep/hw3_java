### Сценарий использования

1. Запрашивает путь до файла-справочника (.csv или .xml).
2. Парсит файл в список записей Address.
3. Выводит статистику:
   - дублирующиеся записи с количеством повторений;
   - количество зданий с 1, 2, 3, 4 и 5 этажами по каждому городу;
   - время обработки файла.
4. Снова ждёт ввод. Выход — команда exit.

Код не падает на битых данных, пропускаются строки если только часть битая

### Общая суть

#### Parser.java

Parser — абстрактный класс с единственным абстрактным методом parseFile:

ConsoleApp работает только с Parser и не знает, CSV внутри или XML.
Конкретная реализация выбирается по расширению файла.

Единственное проверяемое исключение — IOException
XML-специфичные исключения оборачиваются
в IOException. Наружу из любого парсера летит
только IOException. Иначе Parser и ConsoleApp знали бы про XML-библиотеки
что не укладывается в ООП.

Повторения:
Для каждого города — массив из 5 счётчиков (индекс 0 это 1 этаж, ..., 4 это 5 этажей).
Массив создаётся при первом вхождении города.


для подсчета повторений и этажей используется хэшмапа потому что в этой структуре поиск происходит за О(1)
и если у нас будет миллион повторений то обращение к этой записи в мапе будет максимально быстрым.
так у нас общая сложность поиска О(N)
если бы использовали списки то обращение к элементу занимало бы О(N)
а если бы для каждой записи проверяли ее повторения то это сложность в общем O(N^2)


#### Addres.java
Это объект данных который хранит 1 корректную строку. Из Ломбока использовано
@EqualsAndHashCode потому что мы используем хэшмапы и для них нужны методы hash и др
иначе бы сравнивались ссылки которые нигде бы не нашли повторения

Дубликат по заданию — это полное совпадение записи (город + улица + дом + этаж). 
Поэтому ключ в хэшмапе — сам Address.


Этажность: Map<String, int[]>

#### парсеры отдельных файлов 
try (...) только в CSV

FileReader и BufferedReader держат файловые дескрипторы ОС. Если их не закрыть,
приложение может упасть. try (...) — это замена
finally с close(). Использовал именно это потому что когда то давно я увидел такую запись у ИИ и она мне понравилась(как то логичнее)

В ParserXML try (...) не используется: DocumentBuilder и Document
не реализуют AutoCloseable, у них нет метода close(). db.parse(...)
сам открывает и закрывает поток внутри.
